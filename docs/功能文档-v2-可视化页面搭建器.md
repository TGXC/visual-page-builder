# 功能文档 v2：可视化页面搭建器（代号 Studio）

> 基线：`D:\AI工作区\项目\visual-builder`（WebBuilder，单文件 `index.html` 1648 行）
> 定位：在其能力之上做**布局与组件能力**和**AI 能力**两块增强，技术形态改为 Vue 3 + TS + Vite
> 本文是功能文档（做什么），不含实施细节（怎么做）；实施计划另出。

---

## 0. 一句话结论

WebBuilder 是一个「**绝对定位 + 扁平元素 + 内联样式导出**」的自由画布编辑器，它的爽点（拖哪放哪）和它的天花板（不响应式、不可组合、导出不可维护）来自同一个决定：元素只有 `x/y/w/h`，没有父子、没有布局语义。

Studio 要在**不丢掉自由画布手感**的前提下，把数据模型从「扁平元素表」升级为「**元素树 + 布局引擎**」，在这之上加**组件复用体系**（分组 / 容器 / 组件实例），再加一层 **AI**——但 AI 只允许产出 schema 补丁，不能直接写代码，保证「AI 改坏了一键撤销」。

### 1.2 六个结构性短板（每条都有代码证据）

| # | 短板 | 证据 | 后果 |
| --- | --- | --- | --- |
| S1 | **只有绝对定位，没有布局语义** | `:410 elStyle` 恒为 `position:absolute` | 换视口尺寸元素不自适应；文本变长/字体加载后溢出（画布 `overflow:hidden`）；做不到「卡片里放三个按钮且自动排列」 |
| S2 | **元素扁平，没有父子关系** | `:287 pages[{id,name,elements:[]}]` | 不能把一组元素当整体移动/复用；无法做「容器」；`visibleEls()` 只能平铺过滤 |
| S3 | **层级 = 数组顺序，无显式 z-index** | `:771 ctxLayer(d)` 靠 splice 换位 | 精确控制叠放顺序要靠反复「上移一层」；跨页面复制后顺序易乱 |
| S4 | **响应式是假的**：只切画布尺寸，不产生断点数据 | `:1297 handleViewport` 只改 `curW/curH` | 在手机画布上摆好的位置和桌面是**同一份数据**，切回去就错位；没有 per-breakpoint 覆盖 |
| S5 | **无组件复用体系**：15 类写死，无法自定义/组合 | `:324 VALID_TYPES`、`:337 normalizeProps` | 用户重复劳动；不能把自己的作品沉淀成组件；第三方无法扩展 |
| S6 | **导出不可维护**：全内联样式、无类名、无结构语义 | `:1567-1581 buildHtml` 输出 `<div style="position:absolute;left:…">` | 代码体积大、不能复用、SEO/协作差；`CSS` 页签只能写一句「样式已内联」 |

**另外两个工程层面的隐患**（不算功能短板，但会限制进阶）：
- 撤销是**整项目快照**（`:1121`），60 步就是 60 份完整 JSON；元素一多内存与耗时线性涨，且无法做「跳转到某一步」「合并连续输入」。
- 渲染是 `innerHTML` 重建（`:482 renderCanvas`），拖动过程中整画布重绘，元素多了会掉帧。

### 1.3 值得保留的东西（不要重做）

`normalizeProject` 的导入收敛思路（`:372`）、6px 磁吸、双击直接改文字（`:888`）、格式刷、右键菜单、状态栏实时坐标、模板、PNG 导出、`Ctrl+滚轮`只缩放画布（`:1108` 附近）。

## 2. Studio 的目标与定位

| 项 | 内容 |
| --- | --- |
| 一句话定位 | 一个**能画自由画布、也能搭自适应布局**，支持**组件复用**，且**用 AI 加速但不管怎么改都能撤销**的可视化页面搭建器 |
| 与 WebBuilder 的关系 | 能力超集：其 18 项能力全部保留（可导入它的 JSON），在此之上加布局引擎、响应式断点、组件体系、AI 助手 |
| 技术形态 | Vue 3.5 + TypeScript 6(strict) + Vite 8 + Pinia + Vitest；拖拽仍自己写（Pointer Events），不引拖拽库/UI 库 |
| 交付物 | 可运行的 Web 应用 + 导出的静态站点；工程化：类型化 schema、命令式撤销、纯逻辑 core 单测、ESLint 分层、CI |
| 面向场景 | 落地页 / 活动页 / 个人主页 / 表单页 / 简单官网（1–5 页），**不是** Figma 替代品 |

**明确的非目标（YAGNI）**：不做多人实时协作、不做账号后端（本地优先）、不做矢量钢笔/布尔运算、不做任意 CSS 手写、不做后端业务系统（表单提交只给导出与 webhook 挂钩点）。

## 3. 功能设计 · 第一部分：布局与组件能力（核心 1）

> 这一部分解决 S1–S3、S5；配合第 4 部分解决 S4；第 5 部分解决 S6。

### L1 数据模型：从「元素表」到「元素树 + 布局树」

**现状**：`elements: [{id,type,x,y,w,h,props}]`，靠数组顺序定层级。

**目标**：

```ts
// 文档
type Doc = { version: 2; pages: Page[]; symbols: Record<string, SymbolDef>; assets: Asset[]; theme: Theme; breakpoints: Breakpoint[] }
type Page = { id: string; name: string; path: string; root: NodeId; nodes: Record<NodeId, Node> }  // 归一化存储：id → node
type Node = {
  id: string
  type: ComponentType          // 'frame' | 'text' | 'button' | … | 'instance'
  parentId: NodeId | null
  order: number                // 同级顺序（= 层级/z-index）
  layout: LayoutSpec           // 自身尺寸 + 子元素布局（见 L2）
  props: Record<string, unknown>
  style: StyleSpec             // 受控样式（颜色/圆角/阴影/字体…，取代散落的 props）
  overrides?: Partial<Record<BreakpointId, NodeOverride>>   // 断点覆盖（见第 4 部分）
  meta: { name?: string; locked?: boolean; hidden?: boolean }
}
```

**为什么用 `Record<id, Node>` + `parentId/order` 而不是嵌套 children 数组**：按 id 查元素 O(1)、拖拽换父级只改两个字段、补丁只影响一条记录、撤销/协作都更容易——这套「扁平存储 + 父子指针 + order 规范化」的模型我已在另一个项目里用 47 个单测验证过（含 `order` 连续性与补丁往返），可直接迁移。

**验收**：`migrateFromWebBuilderV1()` 能把参考项目的 JSON 完整导入成 v2 文档（页面、元素、props、显隐/锁定、页面名、视口尺寸），且导入后渲染位置与参考项目一致（逐元素 x/y/w/h 相同）。

### L2 布局引擎：自由 + 自动布局并存

**现状**：`elStyle` 永远绝对定位（S1）。

**目标**：每个节点有一个 `layout` 描述，容器的布局模式决定子元素坐标由谁算。

```ts
type LayoutSpec = {
  mode: 'free' | 'vertical' | 'horizontal' | 'grid'   // 容器：子元素排布方式；叶子忽略
  size: { w: SizeSpec; h: SizeSpec }                   // SizeSpec = {kind:'fixed',px} | {kind:'hug'} | {kind:'fill'} | {kind:'ratio',v}
  padding?: Box; gap?: number; columns?: number
  align?: 'start'|'center'|'end'|'stretch'; justify?: 'start'|'center'|'end'|'space-between'
  wrap?: boolean
  position?: { x: number; y: number }                  // 仅 mode:'free' 时使用
  constraints?: { h: 'left'|'right'|'left-right'|'center'|'scale'; v: 'top'|'bottom'|'top-bottom'|'center'|'scale' }  // free 模式下的父级约束
}
```

**核心机制**：布局引擎是**纯函数** `computeLayout(doc, pageId, breakpointId) → Map<NodeId, Box>`，渲染层把算出来的 `Box` 写成绝对定位（渲染依然简单，但模型是流式的）。

数据流：

```
文档树 + 断点 + 画布宽度
        │
        ▼
 computeLayout()  ← core/，纯函数、可单测、无 DOM
        │  Map<id, {x,y,w,h,z}>
        ▼
   渲染层（Vue 组件按 Box 绝对定位）
        │ 用户拖拽/改属性
        ▼
   命令（patch）→ 文档树 → 重新 computeLayout（只算脏子树）
```

**交互要求**：
1. 拖组件到容器内 → 自动成为其子节点（指针几何取最深命中容器，我在另一个项目里用过同款判定并写了单测）。
2. 容器切换模式：free ↔ vertical ↔ horizontal ↔ grid，**切换不丢数据**（free 的 x/y 保留，切回 free 还原）。
3. 拖拽时显示插入位指示线 + 磁吸（保留 6px）+ 等距分布提示。
4. 尺寸模式：hug（包裹内容）、fill（填满父）、ratio（比例）、fixed（固定），拖动时自动推断（拖到内容大小 → hug）。
5. 约束（constraints）：free 模式下的元素绑定父级左/右/居中/拉伸，父级变宽时按约束重算（这是「绝对定位也能响应式」的关键）。
6. 溢出提示：hug/fill 计算后内容超出时在画布上给红色描边 + 属性面板提示。

**验收**：
- 容器改成 vertical 后，子元素坐标由 gap/align 决定；拖动其中一个子元素只改 order，不改坐标。
- 画布宽度从 1440 改到 375：`fill` 元素宽度跟着变、`hug` 元素宽度跟着内容变、free 元素按 constraints 重算。
- 布局引擎 1000 节点整树计算 < 8ms（jsdom 外跑纯函数基准，Node 里量）。

### L3 容器与分组

| 概念 | 行为 | 为什么两个都要 |
| --- | --- | --- |
| **Group（分组）** | 逻辑分组，仍各自绝对定位，整体移动/缩放/复制/显隐；`Ctrl+G` 编组、`Ctrl+Shift+G` 解组 | 用户想「一起搬」但不想改变布局方式时必须有无副作用的工具（Figma 也是这么分的） |
| **Frame/Container（容器）** | 参与布局计算，裁剪溢出、可设 padding/背景/圆角，是布局引擎的作用域 | 「卡片里排三个按钮」这类需求必须靠容器 |
| **自由画布根节点** | 页面的 root 是 `mode:'free'` 的 frame，等价于 WebBuilder 的画布 | 保持「拖哪放哪」的爽点 |

**验收**：编组后拖动组内任一元素 = 整组平移；解组后各自独立；容器删除时子元素一起删（可撤销）。

### L4 组件体系：Symbol（主从）+ 自定义组件 + 插件协议

**现状**：15 类写死在 `DEFAULTS`/`DEF_SIZE`/`VALID_TYPES`（S5），用户无法沉淀自己的作品。

**目标**：
1. **Symbol / Master（主从组件）**
   - 「创建组件」把选中元素抽成 `symbols[id]`，原位置替换为 `{type:'instance', symbolId}`。
   - 改 master（双击进入编辑态）→ 所有实例同步更新。
   - 实例可覆盖「可覆盖属性」：文本、图片 src、链接、颜色（可覆盖白名单由组件声明）；面板显示「已覆盖」标记 + 一键还原。
   - 实例内部节点在文档里**不落库**（由 symbol 展开），保证单一事实来源。
2. **自定义组件（组合式）**
   - 选中多个元素 → 「创建自定义组件」→ 生成一个带 props 的组件（props 来自被选中元素的「提升为属性」标记）。
   - 与 Symbol 的区别：Symbol 是**实例共享同一份内容**；自定义组件是**带默认 props 的模板**，每个实例独立。
3. **插件式组件协议**（可扩展性）

```ts
type ComponentDescriptor<P> = {
  type: string; label: string; category: '基础'|'布局'|'表单'|'媒体'|'数据'|'AI'
  icon: string
  defaultSize: { w: number; h: number }
  defaultProps: P
  propSchema: PropSpec[]            // 属性面板自动生成（沿用我在表单项目里验证过的描述符协议）
  layoutDefaults?: Partial<LayoutSpec>
  render: Component                 // 画布内的 Vue 组件
  toHtml(node, ctx): string         // 代码生成（每类组件自带，解决 S6）
  aiDoc?: string                    // 给 LLM 的一句话语义说明（AI 生成时注入，见第 5 部分）
  overridable?: (keyof P)[]         // 作为 Symbol 实例时可覆盖哪些属性
}
defineComponent(descriptor)
```

**验收**：
- 改 master 文本 → 3 个实例全部更新；实例单独覆盖文本 → 只影响该实例；点「还原」回到 master。
- 注册一个第三方组件（测试里用假组件）→ 组件库面板出现、可拖入、属性面板自动生成、能导出 HTML。

### L7 布局/文档级能力

- **页面树**：不只标签页——支持页面分组、重命名、设置页面路径（`/about`）、默认页。
- **主题（Design Tokens）**：颜色/字号/间距/圆角/阴影定义成 token，元素样式引用 token；改 token 全局生效（这是「设计系统」的最小可用形态）。
- **素材库**：图片/图标上传、本地图库、URL 管理；导出时打包 assets 或保留外链（可选）。
- **SEO/元信息**：页面 title/description/OG 图/favicon；导出时写入 HTML head。
- **模板**：内置模板 ≥ 6 套（登录、落地页、个人主页、定价页、博客列表、表单收集），支持「从模板新建页面」。
- **版本历史**：除撤销外，保留带名字的版本快照（如「改版前」），可对比、可回滚（本地 IndexedDB）。
- **分享/发布**：导出静态站点（zip）或生成分享链接（本地导出 + 可选上传），支持预览链接。

**验收（L7）**：改主题色 → 所有引用 token 的元素同步变色；回滚到「改版前」版本 → 文档完全一致（JSON 逐字节）。

## 4. 功能设计 · 第二部分：响应式与断点（配套核心 1）

**现状**：视口只是画布尺寸，元素数据不分断点（S4）。

**目标**：

```ts
type Breakpoint = { id: 'desktop'|'tablet'|'mobile' | string; label: string; minWidth: number; enabled: boolean }
type NodeOverride = Partial<Pick<Node, 'layout'|'style'|'props'|'order'|'hidden'>>
// Node.overrides[breakpointId] = { layout: { size:{w:{kind:'fixed',px:200}}, position:{x:0,y:0} }, hidden: true, ... }
```

规则：
1. **继承 + 覆盖**：桌面是基准，平板/手机只存差异（默认不写任何东西 = 完全继承）。
2. 编辑某个断点时，改属性**自动写入该断点的 override**，面板上该字段旁出现「本断点已覆盖」圆点，可一键清除覆盖（回到继承）。
3. 容器布局参数（mode/gap/columns）也可按断点覆盖（例如桌面 horizontal、手机 vertical）。
4. 断点切换即时预览，不需要重建文档。
5. 导出：生成媒体查询（media query）或按断点生成独立 class —— 复用同一套覆盖数据。

**验收**：
- 桌面摆好 3 列卡片 → 切到手机 → 把容器改成 vertical + 卡片宽度 fill → 切回桌面布局不变，再切手机仍是 vertical。
- 导出 HTML 里出现对应 media query，浏览器缩窗到手机宽度时呈现手机布局。

## 5. 功能设计 · 第三部分：AI 能力（核心 2）

### AI0 三条铁律（先立规矩，再谈功能）

1. **AI 只产出 schema 补丁，不产出代码**。所有 AI 输出都是 `Patch[]` 或 `PageDraft`（结构化 JSON），经 `normalizeDoc` + 引用完整性校验 + 组件类型白名单后才会落库；校验失败自动重试一次，再失败就原样报错给用户。
2. **每次 AI 操作前先存快照**，操作在历史里显示为一条可撤销命令（带 AI 标签、prompt 摘要）；用户永远能 Ctrl+Z 回到 AI 之前。
3. **离线可用**：不配 API key 时，规则式助手（对齐/间距/对比度/溢出检查）仍然可用；AI 功能在 UI 上明确标注「需要配置模型」。

### AI1 一句话生成页面（从 0 到初稿）

- 输入：`帮我做一个读书会活动的落地页，要报名表单，主色绿色，移动端优先`
- 输出：`PageDraft`（页面 + 元素树 + 主题 token），插入为新页面，可继续编辑（**不是截图，不是 iframe，是真实元素**）。
- 可控性保障：
  - 注入**组件目录**（只注入相关分类的 `aiDoc`，控制 token）；
  - 用 LLM 的结构化输出（tool calling / JSON mode）+ JSON Schema 校验；
  - 生成后跑一遍**本地自检**（元素是否重叠严重、是否超出画布、必填 props 是否缺失）→ 自检失败的结果不落库，而是带着问题去重试。
- 验收：给定 5 条不同 prompt，生成结果**含真实可拖拽元素**、能立即切换断点、能导出 HTML；生成失败时不污染文档。

### AI2 选区指令编辑（最实用，也最适合面试讲）

- 交互：选中若干元素（或一个容器）→ 右键「AI 编辑」→ 输入 `整体再紧凑一点，按钮换成主色，加一句副标题`
- 输出：`Patch[]`（`insert` / `remove` / `update` / `move`），作为一个**命令组**应用，历史里是一条「AI 编辑：整体再紧凑一点」。
- 为什么比「整页重生成」好：改动范围小、可控、可撤销、token 省；局部指令不会把用户其它页面的布置推倒重来。
- 验收：对选中容器执行 3 条不同指令，产出的补丁都只影响选中子树（断言未选中节点 JSON 不变）。

### AI3 设计检查与一键修复（本地规则为主，AI 只做解释）

- 检查项：元素溢出容器 / 文本对比度不足（WCAG AA）/ 间距不成体系 / 同类型元素尺寸不一致 / 图片缺 alt / 移动端断点未覆盖 / 空白过大 / 未使用的组件实例
- 每条问题：位置高亮 + 「修复」按钮 → 走 patch 应用（例如统一间距到 8 的倍数）。
- AI 的角色：把规则结论翻译成人话 + 给出优先级建议（模型挂了也不影响「修复」按钮）。
- 验收：造一个含 5 个已知问题的页面 → 检查面板报出 5 条 → 逐条修复后问题清零，且每步可撤销。

### AI4 文案与素材

- 文案：为选中文本块生成/润色（标题、副标题、按钮文案、SEO title/description），支持语气/长度/语言。
- 素材：按描述生成配图（对接图像模型）或从内置素材库推荐；生成结果写入 `assets` 并保留来源标记。
- 验收：选中标题 → 生成 3 个候选 → 应用其一 → 可撤销；图片生成失败时给出占位图而不是空白。

### AI5 AI 生成新组件（进阶，放最后）

- 输入：`一个带头像和在线状态点的团队成员卡片`
- 输出：一个 **ComponentDescriptor**（props + 渲染模板 DSL）→ 在沙箱里渲染预览 → 用户确认后注册进组件库（本地自定义组件区），可导出。
- 风险控制：只允许使用**受限 DSL**（已有组件的组合 + 受控样式），不允许任意 JS/CSS；生成的组件进不了「内置」区，只能进「我的组件」。

### AI6 工程实现要求

| 项 | 要求 |
| --- | --- |
| Provider 抽象 | `AiProvider` 接口（`complete(prompt, schema) → JSON`），实现：OpenAI 兼容端点 / 本地 Ollama / Mock（测试用固定 JSON）；可切换 |
| 密钥管理 | 只存本地（localStorage）或走用户自建代理；不写入文档、不进导出、不打日志 |
| Token 与成本 | 组件目录按需注入；超长文档只把「选中子树 + 必要上下文」发给模型；调用记录面板显示 prompt 摘要/耗时/token |
| 失败降级 | 网络/配额/解析失败 → 明确报错 + 保留现场 + 提供「重试 / 改用规则助手」 |
| 可测试性 | 所有 AI 流程用 Mock provider 做单测：给定固定模型的返回，断言断言补丁合法、越界引用被拒绝、失败不落库 |
| 安全 | AI 返回的 HTML/文本一律转义后再渲染（参考项目已有 `esc`/`safeUrl` 的先例，导出路径必须沿用它）；不允许 AI 输出脚本/外链可执行内容 |

## 7. 架构与技术选型

```
apps/studio (Vue 3.5 + TS6 + Vite8 + Pinia)
├── src/core/                 纯逻辑，不 import Vue（ESLint 强制），单测覆盖率 ≥90%
│   ├── schema/               类型、normalize、版本迁移（含 WebBuilder v1 导入）
│   ├── layout/               computeLayout（free/vertical/horizontal/grid）、尺寸求解、约束
│   ├── tree/                 树操作：childrenOf / descendants / move / order 规范化
│   ├── patch/                applyPatch / invertPatch（命令式撤销的地基）
│   ├── history/              补丁栈、合并窗口、跳转
│   ├── responsive/           断点解析、覆盖合并（继承 + override → 有效节点）
│   ├── symbols/              Symbol 展开、实例覆盖、循环引用检测
│   ├── codegen/              各组件 toHtml、CSS 生成、Vue/React 导出、静态站点打包
│   └── assistant/            规则式设计检查（纯函数）、AI 结果校验（不依赖具体 Provider）
├── src/editor/               画布（Box 渲染）、拖拽引擎、面板（组件库/图层/属性/布局/断点/主题/AI）
├── src/runtime/              预览渲染（与画布共用组件渲染器）
├── src/ai/                   AiProvider 实现（OpenAI 兼容 / Ollama / Mock）、prompt 模板、调用记录
├── src/stores/               document / history / selection / ui / ai
└── tests/                    unit（core：布局、树、补丁、迁移、检查）+ component（拖拽、面板）
```

选型理由（面试可讲）：
- **Vue 3 + TS + Vite**：与你的主技栈一致（Vue2 → Vue3 迁移叙事自然），且能把已经建好的工程化地基（strict TS、Vitest、ESLint 分层、CI、core 纯逻辑层 + 测试习惯）直接复用。
- **不引拖拽库/UI 库**：拖拽是自己写的 Pointer Events 引擎（可讲清 `pointerdown → 5px 阈值 → 命中测试 → 落点计算 → 提交补丁`），UI 自建 token 体系；这两点都是面试可深挖的技术点，且避免「用别人的库」被问倒。
- **纯逻辑 core + 上层 Vue**：布局引擎、补丁、断点合并、代码生成都可脱离框架单测——这是这套架构最值钱的地方。
- **AI 层独立**：Provider 抽象让「模型可换、可 mock、可离线」，也让 AI 功能不污染核心逻辑。

**与现有表单项目的关系**：布局引擎、树、补丁、历史、描述符协议、校验引擎这些**已验证过的模式可迁移**；表单字段组件与校验引擎会成为 Studio 的「表单」分类组件。仓库层面建议：**新建 `studio/` 仓库**（把现有工程地基配置拷过去），旧仓库保留（里面的补丁/布局/校验代码可作为迁移来源）。

## 10. 风险与代价（写在前面的坑）

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **布局引擎是最难的一块** | 双模式（free + auto）+ 尺寸求解 + 约束，边界情况多（循环引用、hug 与 fill 互相依赖、文本换行影响高度） | 布局引擎做成纯函数 + 表驱动单测；先做 vertical/horizontal，grid 与 hug 依赖文本测量放后面；禁止 hug 与 fill 互相依赖（检测并报错） |
| **组件化与布局的耦合** | Symbol 展开 + 断点覆盖 + 布局计算三者叠加，调试难 | 分阶段：M2 只有树与布局，M3 加断点，M4 才引入 Symbol；每层都有「展开后的有效文档」快照可断言 |
| **文本测量** | 画布里的文本高度依赖字体加载与换行，jsdom 测不了 | 用 `ResizeObserver` 实测 DOM 后回写 hug 高度；无浏览器环境时用估算值 + 标记「估算」 |
| **AI 输出不稳定** | 结构化输出仍可能漂移、超范围引用、编造组件类型 | 三重校验（JSON Schema + 类型白名单 + 引用完整性）+ 失败不落库 + 快照兜底；Mock provider 覆盖全部流程单测 |
| **AI 成本/密钥** | 用户可能没有 key | 规则式助手独立可用（AI3）；key 只存本地；token 与调用记录可见 |
| **范围膨胀** | 这个文档列了 30+ 组件、10 个模块，很容易做不完 | 严格按 M0–M8 推进，每个里程碑都能独立演示；砍需求优先级已定 |
| **导出保真** | 画布渲染与导出 HTML 难免有差异 | 导出与预览共用同一份「有效文档 + 布局结果」，并加视觉回归对比（可选：导出后重渲染截图比对） |
